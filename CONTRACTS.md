# Shop contracts (backend <-> storefront <-> infra)

The Noord Karavane shop copies Soft Rebellion's architecture (Astro SSR storefront + Medusa v2 + Postgres/Redis on DockPi).
Phase 2 built `backend/`, `infra/`, `catalogue/`, `config/`. Phase 3 (storefront) must build against this file.
Anything here that the storefront has to enforce is marked **STOREFRONT MUST**.

## Vouchers (single-use discount codes issued by a signed hook)
Code: `backend/src/lib/vouchers/*` (logic), `backend/src/api/hooks/vouchers/` (routes), `backend/src/workflows/hooks/vouchers.ts` (order lifecycle), `backend/src/scripts/import-vouchers.ts`, `backend/src/scripts/voucher-probe.ts`. Real terms, caps and the secret live only on the Pi (`config/business.json`, `infra/.env`), never in git.

### Endpoints
- `POST /hooks/vouchers`: issue. Body (JSON, strict, unknown keys rejected): `{"program": "<name>", "ref": "<ref>", "email": "<email>"}`. `program` matches `^[a-z0-9-]{1,40}$`, `ref` matches `^[A-Za-z0-9-]{1,40}$` (no underscore), `email` is a valid address of at most 254 chars. The body can never carry terms.
- `GET /hooks/vouchers/report?program=<name>&month=<YYYY-MM>`: report. The program does not need to be in config (so `import-woo` works).
- Both answer **404** while `VOUCHER_HOOK_SECRET` is unset or empty.
- Auth headers: `x-nk-timestamp` (unix seconds, decimal string) and `x-nk-signature` (lowercase hex HMAC-SHA256, 64 chars, key `VOUCHER_HOOK_SECRET`).
  - Signing string for POST: `${timestamp}.${rawBody}` (the exact bytes sent).
  - Signing string for GET: `${timestamp}.${originalUrl}` (path plus query exactly as sent, for example `/hooks/vouchers/report?program=kampi-review&month=2031-07`; never rebuilt).
  - Window: plus or minus 300 s. A replay inside the window is harmless (issuing is idempotent, the report is read-only).

| Status | Body | When |
|---|---|---|
| 201 | `{code, expires_at, value, min_spend, currency: "zar", used}` | created |
| 200 | the same shape | the code already exists for this `(program, ref)` (including a concurrent request that won) |
| 400 | `{"message": ..., "type": "invalid_data"}` | **pre-route**: malformed JSON sent as `application/json` is answered by Medusa's own body parser before the route runs, before the signature check and even with the secret unset. Callers must not expect `{error}` for it. Nothing is written |
| 400 | `{"error": "invalid_body"}` | a correctly signed raw body that is not JSON (for example `text/plain` or `application/x-www-form-urlencoded`), or a body that fails the strict schema |
| 400 | `{"error": "unknown_program"}` | program missing, disabled or invalid in config |
| 400 | `{"error": "program_ended"}` | the program itself ended: a fixed `ends_at` program whose end is not later than now. Nothing is created |
| 400 | `{"error": "campaign_ended"}` | the program is live but a new code's cohort campaign (this SAST month) already ended, for example after its end was edited in admin. Logged at **warn** with the campaign identifier (staff must act). Nothing is created and the campaign is never extended by the hook (that would move every issued code's expiry); to reopen the month, move the campaign's end in admin |
| 401 | `{"error": "unauthorized"}` | missing headers, malformed, bad or stale signature (the reason is logged, never returned) |
| 415 | `{"error": "unsupported_content_type"}` | no raw body to verify: a content type the body parser does not keep (anything but JSON, text or urlencoded, for example `application/octet-stream` or multipart) or an empty body. Checked before the signature. A urlencoded body keeps its raw bytes, so it is not a 415: it gets 401 unless correctly signed, then 400 `invalid_body`. Nothing is written |
| 409 | `{"error": "revoked"}` | the derived code exists but was deleted in admin or is not `active`. Deleting or deactivating a code revokes it; it is never re-minted |
| 429 | `{"error": "cap_reached"}` | the program's cohort campaign already holds `monthly_cap` codes |
| 500 | `{"error": "expiry_unknown"}` | the code's campaign is missing or has no `ends_at`, so no `expires_at` can be given (never an empty string). Logged at error level with program and ref; nothing is created. Fix the campaign in admin |
| 500 | `{"error": "internal"}` | anything else (logged with program and ref, never the email) |
| report 200 | `{issued, redeemed, discount_value_zar}` | |
| report 400 / 401 | `{"error": "invalid_query"}` / `{"error": "unauthorized"}` | |

- `expires_at` is the cohort campaign's `ends_at`; `value` and `min_spend` are the terms stored at issue time; `used` is `promotion.used >= limit`.
- Logging: `vouchers.issue {"program","ref","result"}` with result `created | existing | cap | revoked | ended | campaign_ended | expiry_unknown | error | invalid_body | unknown_program`; `campaign_ended` is logged at warn and adds `"campaign": "<campaign_identifier>"`. For `invalid_body`, `program` and `ref` are logged only when each matches its own pattern, else `null`. Auth failures log `vouchers.auth rejected: <reason>` with reason `missing_headers | malformed | stale_timestamp | bad_signature` (`malformed`: a non-decimal timestamp or a signature that is not 64 lowercase hex chars; `stale_timestamp`: outside the window, so check the caller's clock); the signature and the secret are never logged. A missing raw body logs `vouchers.issue rejected: unsupported_content_type`. The body and the email are never logged; the promotion stores only `metadata.email_hash` (sha256 of the trimmed, lowercased email).

### Config (`business.json` -> `voucher_programs`)
`{ "<name>": { value_zar, min_spend_zar, validity_days | ends_at, code_prefix, monthly_cap, enabled } }`. Name `^[a-z0-9-]{1,40}$`; `value_zar` and `min_spend_zar` positive integers (rand, VAT inclusive); exactly one of `validity_days` (integer 1 to 365) or `ends_at` (ISO datetime **with offset**); `code_prefix` `^[A-Z0-9]{1,8}$`; `monthly_cap` integer of at least 1; `enabled` boolean. An invalid entry is dropped and logged once per process, on the first issue request after boot, whatever program it names (`[vouchers] voucher_programs entry dropped, program "<name>" is OFF until fixed (fix business.json, then restart the server and the worker): <reason>`); it never takes the shop down. Keys starting with `_` are ignored. `config/business.example.json` holds disabled placeholders only. The config is cached per process: **restart the Medusa server and the worker after editing `voucher_programs`**.

### Codes, campaigns, promotions
- Code: `${code_prefix}-${REF}-${S}`, all uppercase. `REF` is the ref uppercased; `S` is the first 7 Crockford base32 chars (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`) of `HMAC-SHA256(VOUCHER_HOOK_SECRET, program + ":" + ref)`, with the ref's case kept inside the HMAC (`abc` and `ABC` give different codes). Every code matches `^[A-Z0-9-]+$`.
- Cohort campaign per program and **issue month in Africa/Johannesburg time** (UTC+2, no DST): identifier and name `${program}-${YYYY-MM}`, `starts_at` null, `ends_at` = the fixed program `ends_at` if set, else the first instant of the next SAST month plus `validity_days` days minus 1 ms. So every code lives at least `validity_days`.
- Promotion: `type standard`, `status active`, `is_automatic false`, `is_tax_inclusive true`, `limit 1`, a fixed `order`-level discount (`allocation across`, `currency_code zar`) of `value_zar`, one rule `MIN_SPEND_ATTRIBUTE gte min_spend_zar`, and `metadata {program, ref, email_hash, value_zar, min_spend_zar, source: "hook" | "import"}`. The hook and the import share one creator.
- **`MIN_SPEND_ATTRIBUTE = "original_item_total"`**, measured on Medusa 2.22.2 + Postgres by the probe: it is the VAT-inclusive, pre-discount shelf total, with or without a tax region, and it survives cart refreshes. `item_total` is post-discount (a minimum on it cancels itself on the next refresh); `item_subtotal` and `original_item_subtotal` are ex VAT once a tax rate exists (a cart exactly at the minimum would fail).
- Staff minting a code in admin (for example a competition prize) must type it in **UPPERCASE**: Medusa matches codes exactly and the storefront uppercases what the shopper types.

### Report semantics
- Campaigns are selected by identifier **prefix** `${program}-${month}`, so for `import-woo` campaigns (`import-woo-YYYY-MM-DD`) the month is the **expiry** month.
- `issued` = promotions in those campaigns (deleted ones excluded).
- A redemption is one `order_promotion` link from one of those promotions (deleted ones **included**, so deleting a code after it was redeemed does not erase the redemption) to an order whose `status` is not `canceled`, that is not a draft order (`status` `draft` or `is_draft_order` true), that has an `order_cart` link (so a converted draft order never counts), **and** whose originating cart carried a line-item or shipping-method adjustment with that code at completion (the same source as the cancel revert; a code added to the order later, by an order edit, never counts). `redeemed` counts redemptions; `discount_value_zar` sums `metadata.value_zar` (fallback `application_method.value`). `promotion.used` is never read, so a cancelled order never counts and a redeem, cancel, redeem sequence counts once. An order linked to a cart that cannot be read is not counted; the report logs `vouchers.report cart not found, orders not counted {"program","month","missing"}` once at warn.

### Store behaviour (measured, Medusa 2.22.2)
- Unknown code on `POST /store/carts/:id/promotions`: `400 {"type": "invalid_data", "message": "The promotion code <CODE> is invalid"}`.
- An existing code that does not apply (below the minimum, campaign ended, already used): **200**, and the code is simply **absent** from `cart.promotions` (discount 0). Medusa does not say why. A code present in `cart.promotions` with no adjustment ("inactive") was not observed but is handled.
- Totals with a code applied: `original_item_total` and line `original_total` are pre-discount; `item_total` and line `total` are **post-discount**; `subtotal` and line `subtotal` are pre-discount (ex VAT once a tax rate exists). **STOREFRONT MUST** show the pre-discount amount as the subtotal before subtracting `discount_total`, never `item_total`, or the discount is counted twice.
- Two carts holding the same unused code that complete concurrently: one order is created, the other completion fails with `Promotion usage exceeds the limit.`.
- A cart update that refreshes the cart (the checkout's `cart.update` with email and addresses) keeps the code but **re-prices shipping**: the courier's free-shipping basis is `item_total`, which is post-discount, so a discount that takes it below the free-shipping threshold turns free delivery into paid delivery and the total goes up. **STOREFRONT MUST** compare the total after that update with the total the shopper saw and stop before payment when it moved.

### Order lifecycle (workflow hooks in `backend/src/workflows/hooks/vouchers.ts`)
- **A cancel gives the code back, for cart orders only, and only what checkout used up.** Only `completeCartWorkflow` registers promotion usage: from the **cart's** line-item and shipping-method adjustments, with the cart's customer and email, and in the same step it links the order to its cart (`order_cart`). A completed cart's adjustments are frozen (Medusa 2.22.2 refuses every cart workflow that touches items, shipping or promotions once `completed_at` is set), so they stay what usage was registered for. Its customer and email are not frozen (`transferCartCustomerWorkflow` has no completed check), which matters only for per-attribute campaign budgets keyed on customer or email; vouchers use none. So `cancelOrderWorkflow.hooks.orderCanceled` reverts only when the cancelled order has an `order_cart` link, and then reverts exactly the codes that carried an adjustment on that **originating cart** at completion (hook-issued, imported or admin-minted), deduplicated, amounts summed, one action per code, with the cart's customer context. A code that appears only on the order's adjustments (added later by an order edit, claim or exchange with `carry_over_promotions`) registered no usage and is never reverted; neither is a code linked to the order without an adjustment. An order without that link (a draft order, converted or not) registered no usage: nothing is reverted and it logs `vouchers.revert skipped (not a cart order) {"order_id","codes"}` (the order's own codes). A link to a cart that cannot be read logs `vouchers.revert skipped (cart not found) {"order_id","cart_id","codes"}` (the order's own codes) at warn and reverts nothing. A cart order whose cart carried no code at completion reverts nothing and, when the order itself carries codes (added later), logs `vouchers.revert skipped (no cart adjustments) {"order_id","codes"}` at info. Medusa 2.22.2 does not revert usage on cancel by itself. Covers the EFT unpaid auto-cancel job, admin cancels and scripts.
  - Logs `vouchers.revert {"order_id","reverted","skipped"}`: `reverted` are the codes whose `used` went down, `skipped` the rest (Medusa reverts only active promotions in a running campaign; a cancel after the campaign ended or after the code was revoked changes nothing, and the report still excludes the order). An unknown order id logs `vouchers.revert skipped (order not found) {"order_id"}` at warn. A failure before or during the revert (including a failed `order_cart` read) logs `vouchers.revert failed {...}` at error level and never fails the cancel. When the revert went through but the read that tells `reverted` from `skipped` fails, it logs `vouchers.revert done, verification read failed {"order_id","codes","message"}` at warn instead.
  - **Staff:** do not apply a customer's code to a draft order (it does not use up the code, so the customer can still redeem it once). On an order edit, claim or exchange of a shop order, **do not carry promotions over or add a code**. This is defence in depth, no longer the only guard: the cancel revert reads the originating cart, so a code added by an edit is never given back. Measured on Medusa 2.22.2: `carry_over_promotions` refuses any fixed promotion whose allocation is not `each`, so an order holding a hook or import code (fixed, `across`) cannot carry promotions over at all.
- **One code per order.** A cart holds at most one non-automatic code. Message, verbatim: `Only one discount code can be used per order.` (HTTP 400, `type invalid_data`).
  - The `updateCartPromotionsWorkflow` validate hook refuses a change that would grow the count past one, on all three store routes that accept `promo_codes`: `POST /store/carts/:id/promotions`, `POST /store/carts/:id` and `POST /store/carts` (measured: all three answer 400 with the message, and no two-code cart is created). Refreshes (add item, quantity, the checkout update) and removals are never refused; re-adding the same code passes.
  - Backstop: the `completeCartWorkflow` validate hook refuses to complete a cart holding more than one non-automatic code (measured with a forged second link: refused, no order, no usage).
  - **STOREFRONT MUST** uppercase codes, derive promo state from `cart.promotions` on every cart object, allow at most one code (automatic promotions, `is_automatic: true`, are not counted) and match the backend refusal with `/one discount code/i`.
- **One handler per hook.** Each Medusa workflow hook takes exactly one handler; a second one anywhere throws `Cannot define multiple hook handlers for the <name> hook` at boot. Any later logic on `cancelOrderWorkflow.hooks.orderCanceled`, the `updateCartPromotionsWorkflow` validate hook or the `completeCartWorkflow` validate hook goes in `backend/src/workflows/hooks/vouchers.ts`.
- **Upgrade check.** After any Medusa upgrade, `grep -n "revertUsage\|promotion" backend/node_modules/@medusajs/core-flows/dist/order/workflows/cancel-order.js` must still print nothing. If Medusa starts reverting usage on cancel itself, remove our revert hook (probe Part A can no longer tell, because our hook is loaded). Then rerun the probe. The revert and the report also rely on two Medusa 2.22.2 behaviours: a completed cart's adjustments are frozen (they stay what usage was registered for), and `carry_over_promotions` refuses a fixed promotion with `across` allocation. After an upgrade, probe Part B S-B14.2b and S-B14.10 to S-B14.12 must still pass.

### Import (cutover, `import-vouchers.ts`)
- `VOUCHERS_IMPORT_FILE=<rows.json> [VOUCHERS_IMPORT_DRY_RUN=1] npx medusa exec ./src/scripts/import-vouchers.ts`. The dry run prints the plan, rejections and campaign extensions and writes nothing. Prints `VOUCHERS_IMPORT_SUMMARY {dry_run, created, planned, skipped_existing, skipped_expired, campaigns_extended, campaigns_open_ended}`. Never commit an import file.
- Rows (a JSON array), prepared from the Woo REST coupon export: `amount` -> `value_zar`, `minimum_amount` -> `min_spend_zar`, `date_expires_gmt` + `Z` -> `ends_at`, plus `program` (for example `import-woo`); keep `code`, `discount_type`, `usage_limit`, `usage_limit_per_user`, `usage_count`, `product_ids`, `excluded_product_ids`, `product_categories`, `excluded_product_categories`, `email_restrictions`, `free_shipping`, `exclude_sale_items`, `maximum_amount`, `limit_usage_to_x_items` under their Woo names. Keep **only** these keys (any other key rejects the row). Copy `amount`, `minimum_amount` and `maximum_amount` **as exported** (decimal strings such as `"50.00"` and `"0.00"` are fine) and keep **every** row, used and expired ones included: the importer decides.
- Fixed order per row: (1) a missing code, or an `ends_at` that is missing, unparseable or without an offset, is rejected; (2) a used coupon (`usage_count` not the integer 0) is rejected **whatever its expiry**; (3) an expired row is skipped (logged) and no other check runs on it; (4) every live row must be a single-use fixed-cart coupon with a minimum spend: `discount_type` `fixed_cart`, `usage_limit` 1, `usage_limit_per_user` null or 1, a whole-rand `value_zar` of at least 1 and `min_spend_zar` of at least 1 (an integer or a zero-fraction decimal string; `"50.50"` is rejected), no product, category or email restriction, `free_shipping` and `exclude_sale_items` false, `maximum_amount` no cap, `limit_usage_to_x_items` null or 0. Duplicate live codes (after uppercasing) are rejected.
- Any rejected row aborts the run: every rejection is printed with its index and reason, the exit code is non-zero and **nothing is written**. A write failure after the plan passed (for example the DB going away mid-run) logs `vouchers.import failed {created, planned, failed_campaign, failed_code, campaigns_extended, campaigns_open_ended, message}` and exits non-zero; the codes before it stay created, and a rerun skips them. Rows are never coerced (a percentage, multi-use or per-product coupon is not translated).
- Codes are uppercased. Codes that already exist (including deleted ones) are skipped, so a rerun is safe. One campaign per program and **SAST date** of `ends_at` (`import-woo-YYYY-MM-DD`), ending at the latest row `ends_at` in that group; a rerun extends an existing campaign's end to a later row, never shortens it, and never touches an existing campaign without an end (open-ended stays open-ended, in the dry run and the real run alike). Dated rows that join such a campaign never expire, so the run warns `vouchers.import warning: dated rows join an open-ended campaign, so they never expire {"campaign","rows_ends_at","codes"}` and lists the campaign in `campaigns_open_ended`; give the campaign an end in admin if that is not intended.

### Accepted drawbacks
- Cap overshoot: counting then creating is not atomic, so concurrent issues at the cap can overshoot by at most (concurrent requests - 1).
- Secret rotation changes every derived code: a repeat `(program, ref)` after a rotation creates a second promotion (it counts against the cap). **Kampi v2 MUST store the codes it was issued and MUST NOT re-request them after a rotation.**

### Probe (real Medusa check; rerun after any Medusa upgrade)
Never against production. It refuses to run unless `VOUCHER_PROBE=1` and the `DATABASE_URL` database name contains `probe` or `staging`. On a throwaway stack (fresh DB, `npx medusa db:migrate && npm run seed`, `BUSINESS_CONFIG_PATH` pointing at a scratch config with enabled test programs `kampi-review` and `probe-cap2` with `monthly_cap` 2):
- Part A (before the hooks file exists, or knowing it records with hooks loaded): `VOUCHER_PROBE=1 VOUCHER_PROBE_PART=attributes VOUCHER_PROBE_MIN=<min> VOUCHER_PROBE_VALUE=<value> npx medusa exec ./src/scripts/voucher-probe.ts`. Needs a fresh DB; deletes the tax region it creates.
- Part B: `VOUCHER_PROBE_PART=service` (service, report, cancel revert including a converted draft order that must give nothing back and an order edit with `carry_over_promotions` whose added code must not be given back, completion backstop).
- Part C, last: `VOUCHER_PROBE_PART=lifecycle` with a scratch config whose `eft_payment_window_hours` and `eft_reminder_after_hours` are 0, passed only to that process (it runs the EFT job, which cancels every unpaid EFT order in the DB).
- Each part prints `VOUCHER_PROBE_SUMMARY {json}` and exits non-zero when a check fails.
